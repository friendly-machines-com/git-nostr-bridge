# Bridge operations

## Runtime contract

The server needs PHP 8.x with bcmath, curl, json, openssl, POSIX, sodium, and
sqlite3. POSIX is required because secret ownership is a mandatory check. It
runs short PHP requests and cron ticks only; there is no daemon.

Production state is `v1/bridge.db`. Deploys must exclude `bridge.db*`,
`*.lock`, and logs.

## UI responsiveness contract

One second is the foreground responsiveness budget. If an operation has not
finished within one second, the page must already show which operation is in
progress. No foreground request or user action may intentionally hold the GUI
for two seconds.

Work involving relays, remote signers, GitHub, retries, or uncertain delivery
must therefore run independently of the GUI as durable background work. Its
transport timeout and overall retry lifetime may be much longer when the
protocol requires it; those timeouts must not become browser response
timeouts. The page observes durable state through fast, read-only requests and
keeps showing the current phase and elapsed time while background work
continues.

For NIP-46 linking specifically, `?wait=STATE` is the foreground status
endpoint and is tested to return in under one second for both waiting and
connected states. The browser starts a separate long-lived approval-listener
POST without awaiting it, and cron remains the durable backstop. Plain page
GET and `?wait=STATE` are read-only; only explicit POST requests may allocate
or bank authentication state. Do not merge relay listening or signer RPC into
`?wait=STATE`.

The account status GET is also read-only. If cookies were cleared, the
user-visible "Sign in with Nostr" action performs two fast POSTs around one
local NIP-07 signature: issue a five-minute challenge, then consume it to
restore the existing browser session. The signed event is not published.
Recovery must not insert links or update nostr_accounts. A repeated full
NIP-46 proof for an existing pubkey likewise restores only the browser session;
rotating the stored bunker/client credentials requires the separately labelled
"Replace remote signer connection" action.

Keep the server clock synchronized. Nostr future-event bounds, OAuth expiry,
queue leases, and Nostr-to-GitHub crash reconciliation all compare timestamps;
in particular, a GitHub object created before a job's durable enqueue is
deliberately ineligible to own that job's hidden marker.

The database contract has no runtime migration path:

- an empty database initializes directly to schema 6;
- a nonempty database must already satisfy the exact current schema-6
  contract marker and shape;
- an unsupported or partial database is rejected without modification.

## GitHub App settings

Use the single Friendly Machines bridge GitHub App for both installation
credentials and optional user authorization.

- Homepage URL: `https://friendly-machines.com/git/`
- Callback URL:
  `https://auth.friendly-machines.com/v1/github/callback`
- Expire user authorization tokens: enabled
- Request user authorization during installation: disabled
- Webhook active: enabled
- Webhook URL:
  `https://auth.friendly-machines.com/v1/github/webhook`
- Webhook secret: exact value returned by `github-webhook.php`
- Installation availability: any account
- Repository permission: Issues — Read and write
- Metadata permission: Read-only (automatic)
- User permission: Starring — Read and write
- Subscribe to: Issues, Issue comment, and Star

Do not subscribe to Watch for repository-star bridging. It is a one-way
legacy event and cannot represent unstar.

GitHub restricted the repository-wide stargazer-list endpoint in July 2026.
Installing an App grants App permissions but does not make the installation a
repository collaborator. The bridge therefore banks each signed Star webhook
in a primary-keyed set of stable numeric repository/user pairs and queries
that user's current starred-repository collection. Hourly work rechecks the
set of all observed pairs, including unstar-before-star pairs. An entirely
missing webhook for a previously unknown actor cannot be reconstructed from
GitHub's restricted repository-wide endpoint; do not make ordinary operation
depend on an organization owner's optional user authorization merely to
bypass that restriction.

After adding the Starring user permission, previously authorized users must
use **Identify with GitHub** on `https://auth.friendly-machines.com/` again so
their GitHub App user token receives that permission. The account page submits
an explicit POST; a GET never allocates OAuth state. Installation tokens
continue to handle ordinary unlinked issue/comment/status crossings, but
GitHub only allows a user token to star or unstar.

The App may be installed on an organization or a regular user account.
Optional user authorization starts from the account page's explicit button.

## Install and reconcile

Install the App on the intended account and select each repository to bridge.
The webhook normally banks the installation ID. Cron also discovers the App's
complete installation set hourly, so initial bootstrap and missed-webhook
recovery do not depend on delivery of that one event. Cron verifies current
installation and repository state through GitHub's API and mints an
installation token. A banked webhook payload alone is not sufficient
authority.

Run cron every minute. This also reduces the gap between live scans for
ephemeral NIP-46 approval responses:

```cron
* * * * * php /home/dh_4nnf3n/auth.friendly-machines.com/v1/cron.php >> /home/dh_4nnf3n/bridge-cron.log 2>&1
```

The adjacent flock prevents overlapping ticks.

Check authoritative App state:

```sh
sqlite3 bridge.db '
  select installation_id,account_login,account_type,status,
         token_expires_at
    from github_installations;
  select github_full_name,installation_id,status
    from github_installation_repositories;
  select id,type,status,attempts,fails,last_error
    from jobs where status <> "done";
'
```

An operational repository must have an active installation, an active
installation-repository row, and an encrypted installation token created by
successful API reconciliation.

## Register the Nostr repository mapping

Publish the repository owner's signed kind-30617 announcement first. Then
register its exact GitHub name, d identifier, owner pubkey, and relay set:

```sh
curl -fsS https://auth.friendly-machines.com/v1/repos.php \
  -H 'Content-Type: application/json' \
  -H "X-Bridge-Secret: $(php -r 'echo require "/home/dh_4nnf3n/secrets/repo-registration.php";')" \
  --data '{
    "github_full_name":"friendly-machines-com/dummy",
    "repo_id":"dummy",
    "owner_pubkey":"64-HEX-PUBLISHER-PUBKEY",
    "relays":["wss://nos.lol"]
  }'
```

Registration checks the newest 30617 across every supplied relay, its
signature, exact d tag, and complete relays tag. The publisher is already a
maintainer under NIP-34 unless it published a subordinate-fork u tag. The
separate bridge key belongs in maintainers only if it should be able to sign a
status for someone else's root.

Successful registration banks the complete signed announcement. Later empty
EOSE responses or relay failures do not unverify it. Cron reduces newer signed
30617 replacements and same-author kind-5 address deletions independently;
every NIP-09 a tag is a deletion target. Content and star deletions use exact
e targets and must never carry the repository address merely as context.

If any relay query is incomplete, registration returns 503 rather than
recording `bridge_status_authorized=false` from an unavailable answer.

## Live acceptance matrix

Verify each applicable row:

| User setup | GitHub → Nostr | Nostr → GitHub |
|---|---|---|
| No user auth | labelled bridge key plus `gh_user` | App installation plus visible npub/event attribution |
| GitHub authorization only | labelled bridge key plus `gh_user` | unrelated Nostr identities still use App attribution |
| GitHub + Nostr linked | user's NIP-46 signer | user's GitHub authorization, with App fallback |
| Nostr link only | labelled bridge key plus `gh_user` | App installation plus visible npub/event attribution |

For GitHub -> Nostr, an active linked signer is an identity invariant, not a
best-effort preference. If the signer is temporarily unavailable, the durable
job remains pending and retries; it must never fall back to the bridge key.
Only an actor without an active GitHub/Nostr link uses the bridge key.

Also verify:

1. GitHub comment before root processing eventually crosses after the root.
2. Nostr comment before root/parent processing remains pending and later
   crosses with the correct tree relationship.
3. GitHub body edit becomes an attributed NIP-22 correction comment.
4. Open, Resolved, and Closed round-trip without an event-arrival assumption.
5. Draft becomes the Nostr status head without mutating GitHub.
6. Same-author comment deletion actually deletes the GitHub comment.
7. Issue deletion becomes a permanent GitHub tombstone when Nostr is the
   source, or a same-signer NIP-09 event when GitHub is the source.

## Queue behavior

- `github_delivery` is the durable webhook inbox.
- waiting `nip46_states` rows are durable pending-handshake state. A kind
  24133 approval response is ephemeral until a live cron scan validates and
  banks it as `connected`. The linking page also listens while open, displays
  a validated signer authorization URL when required, and keeps polling the
  cookie-bound state until completion.
- `nip46_finish` owns all work after approval; the browser may close.
- An ordinary `nip46_finish` for an already-linked pubkey restores the
  cookie-bound browser session without changing the stored signer. Its job
  carries `replace_pubkey` only when the already-identified browser explicitly
  requested signer replacement; a different returned pubkey fails closed.
- NIP-46 `switch_relays` replaces the signer connection's relay set, as the
  protocol requires. The bridge canonicalizes the set, caps it at four
  distinct endpoints, requires clean `wss://` URLs, resolves once, rejects
  private/reserved IPv4 destinations, and connects to that validated address
  while preserving TLS hostname verification.
- missing roots, parents, mappings, App authority, and relay verification
  defer without incrementing `fails`.
- transient GitHub/relay failures stay pending with capped backoff.
- immutable invalid inputs are completed as logged permanent skips.
- repeated non-transient execution failures become `dead` after eight failed
  executions and remain inspectable.

## Supported behavior and limits

- Kind 1621 and kind 1111 are immutable regular events. GitHub edits are
  preserved as new NIP-22 correction comments; the bridge does not disconnect
  an existing thread by publishing a replacement root.
- GitHub issues have no Draft state. A valid kind-1633 Draft remains the Nostr
  head and prevents an older arriving status from overwriting state, but causes
  no GitHub API mutation.
- GitHub's REST API can delete issue comments but has no general issue-delete
  endpoint. Nostr issue deletion therefore produces a visible closed
  tombstone.
- The bridge does not query Git repositories. GitHub/Nostr collaboration
  metadata is sufficient for the implemented issue/comment/status/deletion
  scope.
- GitHub PR/review events, Nostr patch/PR roots, labels, Git tags, repository
  state, and releases are not server-bridge features.
- Relay retention is outside the bridge's control. More than a relay's result
  cap at one exact timestamp cannot be paginated perfectly because Nostr
  filters have no standard offset/tie cursor.
